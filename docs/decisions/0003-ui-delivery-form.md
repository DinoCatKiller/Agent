## 背景

ADR-001 已定「Rust 后端 + GPUI 前端」。实际动手前出现新的判断因素：

1. GPUI 的**表达能力**够用，但**现成样式资源、第三方库与人力供给**远少于 Web/TS 生态。
2. 用户提出 TUI 的可能性 —— 而 **GPUI 无法做 TUI**（见 `X4` §1）。
3. GPUI 上游治理出现不确定性（社区分支 `gpui-ce`、`gpui-unofficial` 高频发版）。

## 备选方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| A：GPUI 原生 GUI（维持 ADR-001） | 同进程零桥接、单可执行文件、原生 Markdown/编辑器/表格现成；体验上限高 | 样式素材与第三方库少；pre-1.0 升级风险；上游治理不定 |
| B：Ratatui TUI | Rust 全栈同进程；开发/验证成本最低；AI 客户端主流形态；纯状态易测 | 体验上限低：无图表/动效，富文本排版受限，图片依赖终端协议 |
| C：Tauri + TS/Web 前端 | 样式资源最多、迭代最快、人力最好找 | 背 WebView（体积/内存/一致性），前后端跨 IPC |
| D：GPUIX（React/TS 驱动 GPUI 渲染） | 理论上兼得「原生渲染 + TS 写 UI」 | 太新、生态空白、多一层 napi 桥故障面 |

## 建议（待你确认后转「已接受」）

**分阶段：先 B（TUI）验证 Core，再选 A 或 C 做 GUI。**

理由：ADR-002 已把契约与 Core 与 UI 解耦，UI 是可替换实现。一期用 Ratatui 能以最低成本跑通「多模型接入 + 流式 + 工具调用 + 会话持久化」这条主干，且不需要在任何 UI 框架的早期风险上押注；二期做 GUI 时，Core 已稳定，选型成本大幅下降。

若「一期必须有富交互 GUI」是硬约束，则退化为在 **A 与 C 之间二选一**（D 作为观察项）。

## 影响

- 若采纳分阶段方案：`agent-ui` 改为 `agent-tui`（Ratatui）先落地，但**接口仍按「UI 无关的事件流 + 命令通道」设计**，为二期 GUI 留位。
- `agent-core` / `agent-common` / `agent-providers` 完全不受影响（这是本方案成立的前提）。
- ADR-001 的「前端 = GPUI」部分被本 ADR 覆盖或顺延。
