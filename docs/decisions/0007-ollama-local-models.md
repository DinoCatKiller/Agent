# ADR-007：Ollama 与「本地模型」的定位

## 背景

`S2` Q5 问「本地模型（Ollama）是否作为一等公民」。`G1` §1.1 把「本地模型（Ollama / llama.cpp）」列入产品目标（本地优先）；但项目所有者的实际用法是**远程 API**——Ollama 走带鉴权的云端 OpenAI 兼容端点，本机不跑 Ollama 服务。即对本项目而言，Ollama 只是 OpenAI 兼容族（`D2`）的又一成员，「本地模型」并非当前真实需求。

需要拍板的是：注册表与路由（`R2`，待创建）要不要为「本地模型」设特殊节点、要不要接 Ollama 原生 API（`/api/tags` 发现、`format` 字段、运行时能力探测）。

## 备选方案

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| A：完整一等公民 | 注册表设本地节点类型（无鉴权 + base-url + 运行时探测），接 `/api/tags` 自动发现 | 本地体验完整 | 需求当前不存在；模型 tag / 能力因机而异，发现与探测逻辑维护成本高 |
| B：半升 | 协议上已覆盖，`R2` 给「无鉴权本地端点」留正式节点类型 | 服务未启动等可用性语义有明确落点 | 为尚不存在的用法预建类型，等真需求来了再定更准 |
| C：**零特化** | Ollama 远程 API = OpenAI 兼容族普通成员；本地形态仅靠现有实现顺带覆盖，不接原生 API、不设特殊节点 | 零新代码；`R2` 按「鉴权 + base-url」建模即可，不必引入「本地/云端」分类维度 | 本地用户体验一般（无发现、无能力探测）；将来有真实需求需另立 ADR |

## 决定

采用**方案 C**。具体边界：

1. **Ollama（远程 API 用法）零特化**：`--provider openai-compatible` + `--base-url` + `--api-key`，密钥正常走 `R1` 流程；`R2` 可按普通云端供应商登记 `ModelSpec`，也可不登记走 base-url 放行（现状 `crates/app` REPL 已支持后者）。
2. **「本地模型」不升级为一等公民**：现有兼容实现已顺带覆盖（`api_key = None` 不带 `Authorization` 头，见 `P1`；REPL 缺钥仅提示不拦截）；不接 Ollama 原生 API，注册表不设本地特殊节点。
3. `G1` §1.1 的「本地模型」目标**保持不变**：能力上顺带存在（兼容协议天然覆盖 localhost 无鉴权端点），语义上不投入。

最关键的理由：**当前不存在本地用法**——为本不存在的形态建注册表类型与探测逻辑，违背「只加这一阶段真的用得上」的依赖原则（`G1` §3）。

## 影响

- 正面：`R2` 设计时无需「本地/云端」维度，按鉴权与 base-url 建模即可；Q5 影响面中「M3 是否先做无鉴权分支」已随 `P1` 完成（`api_key = None`），拍板即闭环。
- 代价 / 后续动作：无近期动作。若将来出现真实本地模型需求（模型发现、能力探测、服务可用性参与降级链），另立 ADR 重开。

## 未决项

无——本决策特有事项均已闭环。
