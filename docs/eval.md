| | |
|---|---|
| ID | `Q2` |
| 类型 | 规格（跨 crate） |
| 状态 | ✅ 已定稿（约定先立，评测集随需要建） |
| 更新 | 2026-10-11 |
| 何时读 | 改 system prompt / 裁剪策略 / 工具描述；换模型；升适配器后想确认「退化了吗」 |
| 规模 | ~1.2k token |

## TL;DR

- `Q1` 管**代码**对不对（契约、解析、错误映射，断网可跑）；`Q2` 管**效果**好不好（模型行为、prompt、工具编排）—— 两者不重叠。
- 效果评测**天然非确定**：目标不是「全绿」，而是**基线对比**（同一套用例上前后的通过率 / 评分差）。
- 三层：**契约级**（结构化输出能否解析）→ **行为级**（该不该调工具、调了哪个、参数对不对）→ **体验级**（人工 rubric）。
- 评测集是**资产**：用例与期望成对存放，并记录**运行模型与日期** —— 模型会变，不记日期的结论会过期。

## 1. 与 `Q1` 的分工

| | `Q1` 测试 | `Q2` 评测 |
|---|---|---|
| 对象 | 代码逻辑 | 模型 + prompt + 编排的**效果** |
| 判据 | 断言（确定） | 通过率 / 打分（概率） |
| 依赖 | 断网可跑（fixtures） | **需要真模型**（花钱、结果有波动） |
| 何时跑 | 每次提交 | 改 prompt / 换模型 / 升适配器时 |

## 2. 评测集

```
eval/
  cases/
    <case-id>/
      case.json          # { id, tier, prompt, expect, notes }
      <附件>              # 可选：多模态输入
  baseline.json          # 最近一次得分快照（对比用；含 model 与日期）
```

`case.json` 的 `expect` 按层不同：

| tier | 期望形式 | 判据 |
|------|---------|------|
| `contract` | JSON Schema | 输出能被该 schema 解析（结构对不对，**不看内容**） |
| `behavior` | 断言列表 | 工具调用序列是否命中（该调哪个、参数含什么、不该调时是否忍住） |
| `experience` | 人工 rubric | 人评分（1–5），只用于少数关键场景 |

## 3. 跑法与判据

- **一次运行 = 固定模型 + 固定 prompt 集 + 固定版本**；结果落 `baseline.json`。
- 判据是**相对基线**：
  - `contract` 层不允许回退（可通过率 100% → 掉了就是 bug）；
  - `behavior` 层容忍波动，但**下降超过阈值**要人工看 diff；
  - `experience` 层不定阈值，只作为发布前的抽样复核。
- **成本**：每次运行都要花钱，所以用例要**少而准**（起步 10–20 条覆盖主路径，不是越多越好）。

## 4. 什么时候跑

| 触发 | 说明 |
|------|------|
| 改 system prompt / 工具描述 | 最直接影响行为，必跑 |
| 改上下文裁剪（`A7`）或摘要 | 影响「模型还能看到什么」，必跑 |
| 换默认模型 / 加降级链（`R2`） | 行为会变，必跑 `behavior` 层 |
| 升适配器或 `mistral`/`anthropic` 协议字段 | 先跑 `contract` 层（便宜），再抽样 `behavior` |
| 发布前 | 三层全跑一次，留一份 `baseline.json` |

**不跑**：纯 UI / 配置改动（`R1`）、纯文档改动 —— 别为无风险的改动烧 token。
