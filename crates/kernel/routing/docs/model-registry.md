## TL;DR

- [`Router`](../../src/lib.rs) 实现 `Provider` 契约：编排层与 UI 把它当一个普通供应商，**感知不到降级的发生**。
- 路由 = 解析候选链 → 能力协商剔除 → 依次尝试；失败分类决定「换下一家」还是「立即失败」。
- 流式降级窗口 = **首个事件**；`Start` 已发出后出错只能传播（中途换流会重复输出）。

## 1. 注册表与候选链

- Router 持有已登记的供应商列表（`with_provider` / `with_erased`），**注册顺序 = 隐式路由优先级**；
- **显式兜底链**（`with_route(target, [(provider, model), …])`）优先于隐式解析；
- **隐式解析**：按注册顺序找「模型清单里有该 id」的供应商，各自成为一个候选；
- 未登记任何 provider id 的显式候选被忽略（配置错误由测试与 `resolve` 长度暴露）；
- `list_models()` = 各供应商清单并集 + **别名合成**（显式路由目标不在任何清单里时，借用主候选的规格换 id）——上下文裁剪（`A7`）靠它查窗口大小。

## 2. 能力协商（`A2` §1）

发请求**之前**，对每个候选做 `required_capabilities(req) × spec.missing()`：

- 清单已登记且能力不足 → 候选被剔除（记入拒绝理由）；
- 清单未登记 → 放行，交给供应商报错（与适配器 `check_model_capabilities` 的空清单语义一致）；
- 全部被剔除 → 同步返回首个拒绝理由（`InvalidRequest`），不发任何 HTTP。

## 3. 降级策略

| 失败类别 | 行为 | 依据 |
|---|---|---|
| `retryable == true`（429 / 5xx / 超时 / 网络断）| 换下一候选 | 供应商侧暂时性问题 |
| `Auth` | 换下一候选 | 密钥 / 权限是**该供应商**的配置问题，换一家可能就好 |
| `InvalidRequest` / `ContextOverflow` / `ContentFilter` | 立即失败 | 请求本身的问题，换模型也救不了（按窗口选型见 §5）|

**透明降级**：被换掉的候选**不产生任何事件**——消费者（UI / 编排层）只见最终结果；候选耗尽时浮出**最后一个**候选的错误。

## 4. 流式的降级窗口

`stream()` 对每个候选偷看**首个事件**：

- 首事件 = 可降级错误 且 还有候选 → 静默换下一家；
- 首事件 = 其它 → 原样转发后续全部事件（含 `Start` 后的中途错误——那只能传播）；
- 无事件即终止 → 视作可降级失败（正常流保证 `Start` 起步，`A2` §4）。

取消（`CallContext.cancel`）：已取消则不再尝试下一候选，直接空流收场（编排层的 `select` 会以 `Cancelled` 收轮）。
