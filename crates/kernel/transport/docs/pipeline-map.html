传输管线 —— 一次流式调用怎么被装起来

传输层只做机制：怎么发请求、怎么切 SSE 帧、怎么收尾、怎么取消、怎么超时。 它不认识任何厂商——「哪一帧算结束」这类供应商语义全部由适配器通过 FramePolicy 注入（D6：机制 vs 语义）。

五段管线每段只做一件事，可单独替换与测试

三分收尾为什么「一帧可以产多个事件」

情形机制行为谁决定
正常帧产出 0..n 个事件，流继续适配器 classify
可恢复坏帧Skip：跳过该帧、流继续、记一条 debug 日志适配器 classify
终止记录产出 0..n 末帧后流正常结束，不再读上游适配器（OpenAI 的 [DONE] / Anthropic 的 message_stop，机制从不解析 data 语义）
EOF 无终止记录调 on_truncated() 把返回值发给下游适配器必须表达「截断」
传输错误上抛 TransportError 后停止，不补任何收尾事件机制固定

一帧多事件不是花哨：契约要求 End 之前必须有一次 Usage（A2 §4），而供应商可能把 usage 与终止原因放在同一条记录里； 供应商干脆不给 usage 时，适配器也要在收尾处补 Usage::default()（Q1 用例 11）。一帧只许产一个事件的话，这两件事无法同时做到。

取消分两阶段（A4 §3） 请求阶段：cancellable(&token, fut) / HttpClient::send —— biased 先看取消，已取消时绝不发起，挂起时立刻放弃。
流阶段：guard(stream, token) —— 取消后产出一次 Cancelled 并结束，取消优先于尚未吐出的帧；这正是让底层连接真正被关掉的那一层。
三种超时（A4 §4） 连接（含 TLS）10s ｜ 整体请求 None —— 流式不设，长回答会被整体超时误杀 ｜ 流式空闲 60s，判据是相邻两帧的间隔而非总耗时。
为什么必须有空闲超时：部分供应商不发结束记录，没有它，一条断掉的连接会让调用方永久挂起。
